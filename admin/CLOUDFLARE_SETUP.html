2. Account, domain, DNS and hostnames

  1. Open Cloudflare Dashboard and select the correct account.
  2. Under Websites, select freetradingbots.com if it is already added. If not, add the domain and follow Cloudflare's nameserver instructions at the domain registrar. Wait for activation.
  3. Open DNS → Records. Check existing @ and www records against your actual website host. Do not overwrite them with guessed IP addresses.
  4. Decide whether to keep the existing workers.dev API URL or use a branded API hostname such as api.freetradingbots.com.
  5. For a branded hostname, open Workers & Pages → your Worker → Settings → Domains & Routes and add a Custom Domain. Use api.freetradingbots.com only if it is not already in use. Cloudflare handles the required hostname configuration for a Worker custom domain.
  6. Test HTTPS for the website and Worker. Update website URLs only after the new hostname works.

3. Worker JavaScript — setup and maintenance

The current Worker already handles more than Mini-RSI. Treat its complete JS file as the source of truth; back it up before edits. The example below is a future pattern, not a replacement for the existing Worker.

  1. Cloudflare Dashboard → Workers & Pages → select falling-sky-7997 (verify exact Worker name in your account).
  2. Open the code editor or deploy from your source repository using your established workflow.
  3. Save a dated copy of the entire existing JS before making changes. Keep GitHub token values out of source code.
  4. Preserve /download, /build/status, premium payment/license endpoints, CORS behavior and /mini-rsi/download.
  5. For future standard bots, prefer one allowlisted registry and one generic route instead of duplicating a long download handler for every bot.
  6. Run a JavaScript syntax check, deploy to a test environment if available, then test old and new endpoints.

5. Cloudflare Turnstile — CAPTCHA setup

Use Turnstile on registration, sign-in, or other abuse-sensitive forms where needed. This section is a setup reference, not confirmation that Turnstile is already deployed.

  1. Cloudflare Dashboard → Turnstile → Add widget. Give the widget a descriptive name and add the exact hostnames where the form runs, such as freetradingbots.com and www.freetradingbots.com. Add a separate testing hostname if needed.
  2. Choose the widget mode appropriate to your form. Copy the site key and secret key.
  3. The site key is public: use it in the browser form's Turnstile widget. The secret key must remain server-side: save it as a Cloudflare Worker secret, for example TURNSTILE_SECRET_KEY. Never place it in HTML or a GitHub commit.
  4. When a form is submitted, send its Turnstile response token along with the form fields to your backend. Before accepting the action, have the Worker verify the token with Cloudflare's https://challenges.cloudflare.com/turnstile/v0/siteverify endpoint.
  5. Reject missing or unsuccessful verification, and check the expected hostname and action where applicable. Tokens expire and are single-use; verify each submission server-side. Rate-limit sensitive endpoints independently.
  6. Use Cloudflare's published test keys in development; use the real site key and secret only in the correct production environment.

6. Database — Bitcoin licenses and optional release metadata

Existing production database: cloudflare-d1-db-btc-licenses. The Worker uses the DB binding and its existing licenses table for verified Bitcoin Premium licenses. Mini-RSI's public installer download does not require a license record. Do not recreate or overwrite this production database.

  1. Cloudflare Dashboard → Storage & Databases → D1 SQL Database (navigation may vary).
  2. Select the existing database cloudflare-d1-db-btc-licenses to view Bitcoin licenses. Only create a separate database for a new development project.
  3. In Worker → Settings → Bindings, verify the existing D1 database binding DB points to cloudflare-d1-db-btc-licenses.
  4. The existing Worker accesses this database as env.DB. Preserve that binding when updating or redeploying the Worker.
  5. Use D1's console or a controlled migration to create tables. Test on a separate development database first.
  6. Enable backups/recovery options available on your plan, and document migration/rollback procedures.

View Bitcoin Premium licenses — actual D1 query

  1. Open Cloudflare Dashboard → Storage & Databases → D1 SQL Database.
  2. Select cloudflare-d1-db-btc-licenses and open its Console tab.
  3. Paste the SQL below and click Execute. It displays the 10 most recently inserted license records.
SELECT * FROM licenses ORDER BY rowid DESC LIMIT 10;

The existing database stores a license_key_hash, the payment transaction ID and license status; it does not store recoverable plaintext license keys. Treat payment identifiers and license records as private. This query is read-only.

Production safety: Do not run DROP, DELETE or example CREATE TABLE statements against the Bitcoin license database unless you have an approved migration and backup.

7. GitHub Actions → Worker → website

Step A · Build

Bot-specific GitHub workflow compiles the Windows engine/dashboard and packages an installer.

Step B · Publish

GitHub Actions uploads an artifact with an exact, documented name.

Step C · Resolve

The Worker finds the latest matching unexpired artifact using the GitHub API and its token.

Step D · Deliver

The Worker streams the ZIP. The website button points to the Worker URL.

8. Deployment and verification

  1. Back up the current Worker JS and export any existing database schema before editing.
  2. Verify the intended Worker/environment, bindings, secrets and route list.
  3. Make one small change; run syntax validation. Avoid placeholder blocks or duplicate if routes.
  4. Deploy and inspect Cloudflare's deployment status/logs.
  5. Test Worker health, Mini-RSI ZIP download, existing /download and /build/status, then premium authorization and payment flows in their appropriate test mode.
  6. Check the website download button from an incognito browser and verify the downloaded ZIP contains the intended installer.
  7. If changing hostnames, test the new domain and HTTPS first; only then update website links. Keep the old hostname until migration is complete.
