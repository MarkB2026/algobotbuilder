3. Settings, permissions & secrets

WhereWhat to configureImportant
Settings → Actions → GeneralActions permissions, allowed actions, workflow permissionsGrant only permissions required by each workflow. A build that only uploads an artifact normally needs read access, not broad write access.
Settings → Secrets and variables → ActionsRepository or environment secrets used by GitHub ActionsNever paste secret values into YAML, screenshots or this document.
Settings → BranchesDefault branch and protection rulesCurrent examples use main; check actual branch before dispatching a workflow.
Settings → EnvironmentsOptional protected production release environmentUseful later for manual approvals or production signing credentials.
GitHub → Developer settings → Personal access tokensFine-grained token if an external Worker needs repository artifact accessToken is stored in Cloudflare Worker secrets, not on the public website. Give it minimum required repository permissions.
Current integration: Your Cloudflare Worker uses a GitHub token binding (GITHUB_TOKEN) to query and stream GitHub Actions artifacts. That is a Cloudflare secret; it is not the same as a GitHub Actions repository secret.

GitHub token checklist

For private-repository artifact access, confirm the token's repository selection and Actions read permissions. If it expires or is rotated, update the matching Cloudflare Worker secret and redeploy as required. Do not record token values in this guide.

4. Run a Windows installer workflow

1

Open Actions.

2

In the left sidebar, choose the Mini-RSI workflow (the display name comes from the YAML name: field). If the sidebar is collapsed, expand it.

3

Click Run workflow, select the intended branch (normally main), fill in any workflow inputs and click the green Run workflow button.

4

Refresh the workflow runs list if the new run does not immediately appear. Open the newest run.

No Run workflow button? The workflow needs workflow_dispatch: under on:, and the workflow file must be available on the repository's default branch. You also need sufficient repository access.
name: Build Mini-RSI Windows Installer
on:
  workflow_dispatch:

jobs:
  build:
    runs-on: windows-latest
    steps:
      # checkout, Python setup, dependencies, PyInstaller,
      # Inno Setup and artifact upload belong here.

The YAML above illustrates the manual-run trigger; it is not a replacement for your working build-mini-rsi.yml.

5. Open the build and inspect failures

1

From Actions, click the workflow and then the specific run. The run's Summary page shows the overall result.

2

Click the build job (its name depends on your YAML). Expand individual steps to see checkout, Python dependency installation, PyInstaller, Inno Setup and artifact upload logs.

3

If a build fails, find the first failing step and read its actual error before changing code. Check the referenced file path, dependency name, tool version and output location.

4

Return to Summary after a successful run to locate the finished artifact. Do not confuse the build job log with the run summary.

Artifact names are exact-match identifiers in the current Worker. Changing the upload name in YAML without updating the Worker can break downloads. GitHub artifacts are ZIPs; a permanent direct EXE link requires a release asset or separate storage.

Artifact upload example

- name: Upload installer
  uses: actions/upload-artifact@v4
  with:
    name: MiniRSI-Windows-Test-Installer
    path: path/to/MiniRSI_Setup.exe
    if-no-files-found: error
    retention-days: 30

Illustrative upload step. Verify the real EXE output path and retention settings in your workflow.

7. Bulk-renaming files — the safe repeatable method

Historical note: We discussed and performed mass filename changes during the bot setup, but the exact original rename command and full old→new mapping are not available in this guide's verified record. The procedure below documents a safe way to repeat that operation without guessing what was changed previously.

A. Create a rename map first

Use a CSV with the exact old and new relative paths. Keep a copy alongside your migration notes. For large changes, make a new Git branch first.

old,new
mini_rsi/OLD_DASHBOARD.py,mini_rsi/mini_rsi_dashboard.py
mini_rsi/OLD_ENGINE.py,mini_rsi/mini_rsi_engine.py

These are illustrative placeholders, not claims about your original filenames.

B. Windows PowerShell — preview every change

git switch -c chore/rename-bot-files
$map = Import-Csv .\rename-map.csv
foreach ($item in $map) {
    Write-Host "WOULD RENAME: $($item.old) -> $($item.new)"
    if (-not (Test-Path -LiteralPath $item.old)) {
        Write-Warning "Missing source: $($item.old)"
    }
    if (Test-Path -LiteralPath $item.new) {
        Write-Warning "Target already exists: $($item.new)"
    }
}

C. Apply with Git so moves are tracked

# Run only after reviewing the preview and fixing collisions.
$map = Import-Csv .\rename-map.csv
foreach ($item in $map) {
    git mv -- $item.old $item.new
}
git status --short

D. Update all references, not just the filenames

Search your source and configuration for each old basename and update imports, executable paths, PyInstaller .spec files, Inno Setup .iss files, workflow YAML, dashboard launch commands, JSON paths and documentation. In VS Code use Ctrl+Shift+H for Replace in Files, review the preview, then apply. Avoid a blind global replacement when short names appear in unrelated code.

# Find leftover old names in tracked text files
# Replace OLD_DASHBOARD / OLD_ENGINE with your actual old names.
git grep -n -e 'OLD_DASHBOARD' -e 'OLD_ENGINE'

# Inspect the actual rename and reference changes
git diff --stat
git diff --check

# Commit only after local checks and a successful GitHub build
git add -A
git commit -m "Normalize Mini-RSI filenames and build references"
git push -u origin chore/rename-bot-files
Critical Windows caveat: Git may ignore case-only renames on case-insensitive filesystems. Use a temporary intermediate name with git mv twice (e.g. git mv old.py temp_rename.py, then git mv temp_rename.py New.py) and verify git status.

E. Validate the full chain after renaming

Confirm Python imports, build inputs, installer source paths, output EXE names, artifact upload paths, Worker artifact-name mapping and website URLs. Then run the workflow and install the ZIP's EXE on a clean Windows test machine.

8. Template for every future bot

1. Source

Own folder, engine, dashboard, default JSON plan, requirements, README.

2. Build

Own .github/workflows/build-<bot>.yml, PyInstaller spec, Inno Setup script.

3. Publish

Unique, stable artifact name; build succeeds; ZIP contains correct installer.

4. Distribute

Register bot in the Worker, add website button, test end-to-end download.

Architecture note: Mini-RSI uses a shared prebuilt installer. The existing configurable Basic/Premium/Reversal builds may use per-build artifact IDs, payment checks and license logic. Preserve those existing flows when moving to a reusable bot registry.

Future release improvement

Once a bot is stable, consider publishing versioned GitHub Release assets rather than relying solely on expiring Actions artifacts. Use separate test and production release workflows and never expose signing keys or GitHub tokens in public files.

9. Troubleshooting reference

ProblemCheck first
Run workflow button missingDoes YAML contain workflow_dispatch? Is it on the default branch? Do you have write access?
Build fails on missing Python fileWas a file bulk-renamed without updating imports, workflow path or PyInstaller spec?
Inno Setup cannot find EXECheck PyInstaller output directory, EXE basename and .iss source path.
No artifact on SummaryCheck whether upload-artifact ran and whether path: matched the built installer.
Worker returns “installer not published”Compare exact artifact name, expiry and repository; inspect latest workflow run.
Worker returns 401/403/502Check GitHub token permissions, expiry and Cloudflare Worker secret binding.
ZIP downloads but no installerInspect upload-artifact path and verify the ZIP contents before publishing.
Website download button failsVerify the deployed Worker route, CORS if applicable and actual button URL.
