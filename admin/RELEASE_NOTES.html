02 / Trading bots

Standard distribution: GitHub Actions builds Windows installers; Cloudflare Worker delivers the matching artifact ZIP. Customized Basic/Premium builds and licensed bots retain their separate authorization workflow.

Download working in our testInstaller workflow

Mini-RSI Bot

Independent RSI bot, separate from the premium RSI-divergence Reversal Bot. This became our reference workflow for publishing future bots.

  • Repo folder: mini_rsi/; workflow: .github/workflows/build-mini-rsi.yml.
  • Confirmed artifact: MiniRSI-Windows-Test-Installer; installer: MiniRSI_Setup.exe.
  • Worker download: /mini-rsi/download; user receives a ZIP containing the Windows installer.
  • Local dashboard; JSON plan import/export from the website builder; MARA baseline; IBKR OBSERVE and PAPER; one-share safety override.
  • UI request: one START BOT / STOP BOT toggle, STOPPING… state, REFRESH; align Strategy Settings and Latest Decisions.
  • Stop request must not be mistaken for flattening positions. Software-managed stops do not operate while the engine is off.
Worker installer download ↗ · Confirmed Actions artifact ↗
Release verification
  • Confirm latest installer includes the revised START/STOP interface; a successful download alone does not confirm the latest UI is inside the EXE.
  • Rebuild before publishing source-code changes; test IBKR connectivity, stop latency, OBSERVE/PAPER and install/uninstall.
  • Actions artifacts expire: migrate approved permanent builds to Releases or object storage when needed.

BeeBot + The Hive

BeeBot is the renamed AllBot stock long/short system; The Hive is the optional community data-sharing concept.

  • AllBot baseline discussed through v1.4.9, including forced PAPER execution test, one-share override and DU paper-account guard.
  • Configurable strategy/execution separation, local dashboard and plan JSON.
  • Each user retains a local trade database; optional sharing to The Hive.
  • Proposed shared schema includes trade context, ATR consumed/remaining, decisions, candidate popularity and performance.
  • Ownership rules must prevent two bots from managing the same position without an explicit handoff.
  • Keep engine and dashboard version numbers synchronized on every release.
Before a public installer
  • Confirm live-trading guards and the exact behavior of one-share override.
  • Document ownership conflicts, adopted positions, risk limits and local/Hive data consent.
  • Publish under BeeBot naming consistently; retain old AllBot names only where migration requires them.

03 / Shared infrastructure and companion apps

Bot Settings Console & Ownership Registry

  • Shared JSON ownership prevents accidental overlapping management across OmniBot, ZeroDTEBot, WheelBot and other bots.
  • Allow intentional adoption of otherwise unclaimed positions; show a clear conflict/rejection reason.
  • Settings Console discussed around v1.78; Control Panel around v1.9. Verify source files before publication.

IBKR Trade Dashboard & Option Plot

  • IBKR Trade Dashboard development reference v3.1.20.
  • Separate Option Plot development reference v11.27; do not assume this equals the publicly released Dynamic Options Plotter v1.13.
  • Keep IBKR ports, client IDs and account credentials out of public defaults and screenshots.

The Hive: local + optional shared database

  • Each user has a local database recording the same trade schema used for optional community contributions.
  • Share only with explicit opt-in; define anonymization, retention, schema version and ownership rules before launch.
  • Candidate scans can incorporate community popularity once enough reliable data exists.

Website builders & downloadable configurations

  • Mini-RSI website builder exports JSON imported by the installed local dashboard.
  • Broader dropdown-driven bot builder concept: choose strategy parameters, generate a plan and build a local installer.
  • Website brands discussed include FreeTradingBots.com, AlgoBotBuilder and BotScripts; naming and deployment are separate decisions.
  • Local installs require dependencies and runtime packaging; test clean Windows machines rather than relying on developer environments.

04 / Our publishing standard

StepTrading tools — GitHub ReleasesTrading bots — Actions + Worker
SourceVersioned tool source and installer configurationIndependent bot folder, engine, dashboard, plan, installer config
BuildRun Windows build workflow; create EXE installerRun bot-specific GitHub Actions workflow
DistributionAttach EXE to a named GitHub ReleaseUpload named Actions artifact; Worker streams ZIP
WebsiteDirect GitHub Release asset URLBot-specific Worker download URL
ChangesRebuild EXE, increment version, publish a new releaseRebuild installer, confirm artifact name and Worker route
DurabilityRelease assets persist until removedActions artifacts expire; archive approved builds long-term
PremiumOnly if the utility actually needs licensingPreserve checkout, license checks and custom-build authorization
Do not add a new Worker route for every future bot unless needed. The Mini-RSI route works now. A later shared bot registry can map bot IDs to artifact names while preserving existing Basic/Premium endpoints. Make that migration separately from feature releases.
